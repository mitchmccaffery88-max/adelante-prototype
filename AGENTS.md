# Architecture rules

- Credentialing uses ehr-ext records, roster NPI and registry writes; transition audits are ids-only, Today reads claim counts, Billing stays projected. DEA reads the existing service catalog through self-registration, never booking flags, SUD inference or wider Billing allowlists. Why: one service classification cannot disclose clinical context or split authority.

- Phase 2 stays disconnected; commands/unproved reads stay closed. Access entry uses matched team/reason helpers; chartPart2Boundary self-registers relationship facts into the unchanged matrix gate. Reason-only Part 2 requires class-specific consent; direct internal-use is counsel-pending. Why: entry cannot replace matrix grants or split app/SQL rules.
- Approved source re-pins hash-check prior text once. Why: no drift.

- Daylight public destinations use the existing AppShell public allowlist and WebsiteLayout; existing member resources keep their route and shell, and missing marketing destinations use WebsitePlaceholder with leaf metadata. Why: new public menus must resolve without reclassifying member/staff workflows.

Standing rules — apply to ALL work, every change, any folder:
- Registry + runAction: every mutation is a `CHART_ACTIONS` entry run through `runAction` (role check + one audit event).
- Simulated: every mock/placeholder integration has `simulated: true` in `features.ts`, audits `simulated: true`, UI says "Simulated".
- SimulatedBadge presents shared integration labels only; member hosts pass their existing language and shells own the translation-review notice. Why: labels cannot change actions, gates or real manual verification.
- Part 2: SUD content is hidden (not stubbed) for roles failing the existing checks; notification/audit/task text stays neutral; outbound SUD goes through `disclose()`.
- Draft: every clinical/policy rule is labelled "Draft — pending clinical sign-off"; Spanish clinical copy marked draft.
- Cohort guard 11 on all aggregates.
- Outpatient only: in-facility behind `inFacilityEnabled()`, off by default.
- Demo seeds only through real store functions.
- B2-5 consent migration queues scoped demo captures until the registry runner is ready; legacy-history marking uses the migration registry entry, and named-form publication uses the existing form actions. Why: initialization must not bypass registry checks, invent historical signatures or duplicate captures.
- Legacy consent marking (`consent_legacy_migrate`) runs only as the non-staff system migration actor from `consentMigration.ts`, hidden for every staff role and refused by the store for anyone else. Why: no staff role may mark history, while the migration still goes through the registry with one audit.
- Consent gates prefer applicable typed evidence; otherwise read only an explicitly mapped live untyped section, never flag callbacks. Live section writers retain their audit path and attach only actual signature provenance. Why: legacy migration must not revoke today's workflows or invent signed documents.

- Member status chips are presentation-only and display existing record labels; shared clinical components opt in through existing audience/actor boundaries. Patient help opens the existing sheet in CrisisHeader; advocate header help is a direct 988 phone link. Spanish translation-review notice is owned once by the member shell. Member text-button wrapping is scoped to member shells/overlays, preserves square icon controls, and Home tiles must shrink to available width. Why: member presentation cannot change staff rendering, permissions, lifecycle rules or expose patient help to advocates.

Subdirectories have their own AGENTS.md (`src/lib/`, `src/components/`) — read before changing files there.
- Staff interface English is a non-persistent context override in AppShell; content previews retain their own local language context. Why: staff navigation must not rewrite member preferences or patient-directed output.
- StaffShell owns compact staff chrome and StaffDensity React context marks its portalled overlays; existing route launchers portal their trigger into the shell's New slot without moving their forms, registries or event handlers. Why: staff sizing and a single create entry cannot change member rendering or chart/action permissions.
- Ordinary screen Spanish lives in each screen's existing dictionary or local bilingual copy object; the source-only review exporter retains stable UI keys and a reviewed audience-exclusion manifest. Why: staff-only branches and controlled text must not be translated by member screen-gap drafting.
- Staff care-work and operations status chips derive presentation from existing record statuses and acting-person ownership, with English record labels; shared member branches, denied-claim styling, simulation, policy and KPI exceptions remain isolated; ambiguous operations statuses retain their existing display. Why: colors cannot change ownership, permissions or workflows.
- Resource verification and existing listing edits share the community-resource view in `/admin-content`; verification uses `runAction("resource_verify")` and the existing verifier/store gates. Why: one listing workflow, unchanged role access and published revision provenance.
- Both patient check-in hosts render EmotionCheckIn; checkInCopy owns its bilingual words, patientCheckInContext projects visible real records, and privateSelfTrackingActions runs self-only writes with generic audit metadata. Why: one flow and dismissal source, no private-answer disclosure or automatic navigation.

- Staff FormField/ConfirmDialog own presentation only; confirmedAction runs the registry once with a scrubbed reason; stores own lifecycle audits. Why: no duplicate mutations or disclosed answers.
- StaffShell measures the demo bar for sticky clearance; compact coarse-pointer header and sidebar anchors retain real touch bounds. Why: growing demo controls and safety counts must not obscure staff actions or expand the phone document.
- Staff ordering uses caller-gated children and host-owned summary slots; My work crisis uses header role scope; tables keep host gates, statuses, editors and handlers. Why: regrouping cannot widen access, duplicate mounts/audits or change excluded screens.
- Staff shell and demo controls render role-dependent content only after the acting role is known; no access decision, redirect or audit runs before it; no role/clock output in server render. Why: demo role lives in browser storage.
- Browser suite: --workers=1 against dev server :8080. Why: parallel runs cause false timeouts.
- Personal quick-action preferences are presentation-only device settings in quickActionPrefs, read after hydration and scoped to the acting staff identity, with no registry mutation or audit; selection uses existing launcher inventories and role-assignment/registry gates; current-role items without a local handler are omitted, and other-role items remain disabled until switched. Content launcher IDs are shared in quickActions. Why: preferences cannot grant access, reroute handlers or touch patient records.
- Public landing sections and reusable ReadyBand live under the existing WebsiteLayout; public siteConfig controls display-only hero/confirmed-footprint output, and Ask Adel uses a pure bilingual classifier plus anonymous client-only intent counts without storing raw questions or running clinical actions. Why: scripted public navigation cannot enter patient records, audit medical text or change care permissions.
- WebsitePage and data-driven JourneyPage reuse landing tokens and ReadyBand; publicDirectory projects the existing managed resource store and naloxone entries, and append-only anonymous reports enter ResourceVerificationQueue via a non-staff registry principal. Why: public filters/editor metadata cannot change member directory permissions, invent verification or collect patient identity.
- Public website motion lives in src/lib/website/motion.ts (one reduced-motion check, reveal/magnetic installers) plus daylight.css; hidden reveal states are added only by JS after IntersectionObserver and motion checks, and focus reveals immediately. Why: content stays visible without JS and with reduced motion, and the 988 bar/header actions are never covered or delayed.
- Remaining public information pages share WebsiteSections, and batch copy is merged from i18n.website4b into the existing website dictionary; platformCapabilities owns display-only status data. Why: bilingual page content and status disclosure stay isolated from clinical gates.
- Website careers/contact append preview-only, non-patient items through website_intake_submit; websiteInbox retains résumé name/size only and projects rows into the existing Inbox for the acting demo admin, with no persistence or production authorization claim. Why: public intake cannot grant staff access or place raw text in audits or patient queues.
- Public referral step state only controls existing section visibility; final validation/store/delivery remain in ReferralSubmissionForm and staff retain the single-page form. Why: public presentation must not change referral rules, fields or transport.
- Staff referral sending UI and registry/store use canSubmitReferral, separate from contact/disposition permissions. Why: a narrow sending exception cannot widen care-coordination grants or produce dead controls.
- Website signup uses pure signupMatch rules and the public-signup-only registry store; an account needs one possession proof (staff invite link to the contact on file, a verified typed contact, or staff in-person confirmation), invite tokens live hashed in signupInvite, and verified-contact or paper-code matches reuse enrollment while mismatches create Identity review items without public disclosure. One SignupFlow hosts public steps and retains the assisted operator branch. Why: prototype matching must not grant staff access, disclose existing records or create unverified accounts.
- HLOC typed capture accepts explicit required-element confirmations, actual signature date and expiry; the staff panel runs the dedicated registry entry. Why: known purpose/destination cannot imply missing Part 2 evidence.
- Identity review and account support are separate queues; identity decisions validate acting-role reviewers, candidate membership and restricted access in the store, and confirmed merges reuse the existing consent-holding merge engine. Why: queue presentation cannot disclose candidates or widen record decisions.
- Staff held roles are primary plus explicit additional assignments, never a permission union; Intake Phase A uses referral-only booking/group/completion/initial-assignment adapters in intakePhaseA and source-keyed receipt-only escalation in intakeTriage, with no record-class grants. Existing booking checks and clinical group approval remain authoritative; triage uses existing Today/Escalations surfaces. Why: front-door responsibilities cannot grant general chart access or create fake patients.
- Intake Phase B uses intakePhaseB for capability-checked linked-patient form sends/captures and Billing-owned requests/status; intakePacket owns validated referral staging, source-bound checklist and restricted documents, with completion plus existing care-team record checks for handoff. Existing ledger/chart/importer grants remain denied and hooks fail closed. Why: administrative intake cannot become clinical access or result entry.

- Public mission uses one website dictionary key; core values/services/caption slots use dianaConfig and bilingual Diana strings, with one assistive values list and reduced-motion static output. Why: ongoing copy edits stay consistent across Home/About without changing clinical workflows.
